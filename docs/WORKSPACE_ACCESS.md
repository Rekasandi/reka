## Implemented and locally verified

- `apps/api/src/common/access/workspace-access.ts` centralizes canonical membership checks, SQL visibility predicates and read/write/management authorization. Explicit actor arguments work with the existing Neon HTTP driver; no interactive transaction or ambient session settings are assumed.
- AuthGuard requires an unexpired session plus exactly one active workspace membership. Authorization uses `organization_members.role`, never a body-supplied actor or a mutable global `users.role` label.
- Ordinary team, issue, project, cycle, label, search and activity queries are filtered server-side. Owner/admin do not automatically see private content. Inaccessible private detail reads return 404 without exposing names/metadata.
- Issue creation/edit/deletion and comments validate team access. Team viewers cannot mutate issue/comment content. Parent/project/cycle references cannot link unauthorized or wrong-team resources; hierarchy cycles are rejected. Estimates of zero are preserved.
- **User-confirmed:** owner/admin/member can create teams and self-join public teams; the creator is explicitly enrolled as lead. Only authorized members manage private membership: lead or owner/admin already belonging to the team. Private non-members cannot use public self-join or administration to bypass membership.
- **User-confirmed:** existing guest/client labels and accounts remain internal read-only identities, without an external portal. Explicit private membership still permits read access; even a legacy team-lead label does not grant shared write permission. A global guard blocks shared HTTP mutations for those roles; personal Inbox read/delete state remains usable.
- Project membership/repository management requires an authorized project/team lead or workspace administrator, plus explicit private-team visibility. A project membership cannot grant implicit access to a private team.
- Cycle planning/management requires team lead/admin permission; a rollover target must be an accessible different open cycle in the same team. Full atomic scheduling/rollover/history remains the Cycles milestone, not proved here.
- Personal notification reads/counts/mutations re-check current resource permissions. Previously stored private notification text remains preserved but disappears from the API after membership revocation. Event creation excludes unauthorized/deactivated recipients.
- Workspace invitation issuance/list/revocation and acceptance are persisted. Issuance returns a copyable 1–30-day link once; only SHA-256 hashes are stored. Acceptance checks verified GitHub email and consumes the invitation, grants membership and creates a session in one SQL statement. Expired, revoked, wrong-identity and replayed links fail.
- GitHub OAuth now uses a hashed one-use ten-minute state nonce plus an HTTP-only browser cookie, requests `user:email`, ignores public/unverified email claims, and binds a stable numeric GitHub ID. Existing approved legacy identities retain their roles; uninvited new identities cannot enroll. A bound ID/email cannot be reassigned by profile editing. No first-login owner promotion exists.
- Legacy demo/passkey routes remain explicit, but demo impersonation is denied and former fabricated passkey-option payloads return honest unsupported errors. No passkey verification workflow existed; GitHub remains the supported login. Existing credential records are untouched.
- Production cookies use secure `__Host-` names. Cookie-authenticated mutations require the configured WEB_URL origin; strict Bearer authentication remains available to non-browser clients. Exception logs and JSON error paths omit sensitive query URLs/SQL stacks.
- Canonical workspace role updates and deactivation are owner/admin-only. Only an owner manages owner roles. A native last-owner trigger protects update/delete, touching the organization row to serialize removals; PGlite/HTTP tests exercise rollback and concurrent requests. A separate native Neon test now proves overlapping PostgreSQL sessions at READ COMMITTED, REPEATABLE READ and SERIALIZABLE cannot remove both owners.
- Users reads use canonical membership and visibility-filtered issue/team counts. Manual profile creation remains persisted, with inactive `pending` admission; activation/ownership cannot bypass verified invitations. User DELETE now deactivates without deleting authored work, assignments or identities. Existing membership admission defaults to `legacy`; invitation acceptance records `invited`.
- Clients/contacts and Organizations reads/writes use current company scope. Client-linked private projects and derived counts are visibility-filtered; client plus optional validated contact are created atomically.
- Actual Users controls now issue invitation links, update canonical roles and deactivate/reactivate permitted accounts. Settings includes persisted workspace name/invitation management. Login forwards invitation intent to OAuth. Existing user-record creation remains a separate, honestly labeled action.
- PR linking now selects only repositories available to the issue/project and current actor, verifies the requested PR against GitHub's repository ID, persists provider-verified branch/URL/title/state, and updates issue status/history. The collaboration browser suite drives the UI→Nest→isolated Postgres path with a controlled GitHub API response; this proves the contract/data flow, not live provider behavior. Branch creation status changes are driven by verified webhook events, not clipboard copy; live delivery is unverified.
