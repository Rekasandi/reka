# REKA — core Linear workflow implementation matrix

Baseline: goal `mv6rv5a2-43ym1x`, confirmed 2026-10-13. This is functional parity for the agreed core workflows, not a clone of Linear's visual design, proprietary implementation, or entire commercial product. Later Linear releases do not automatically expand this inventory.

## Scope and visual constraints

Single internal-company workspace, multiple employees, GitHub login retained. Owner/admin/member roles, private teams, comments, mentions and notifications are required. Existing Clients remain internal records, not an external client portal.

Use React/Vite, NestJS, Drizzle, the existing worker, shadcn `@reka/ui`, Tailwind and `DESIGN.md`. Preserve existing routes/data and unrelated working-tree changes. Keep the agreed Projects table without outer card/frame, description or identity icons; compact metadata on the right. Team identity uses its key. Keep inline editing, selection/nesting behavior, category filters, sans UI and monospace code.

Excluded: billing/payment/pricing, SaaS subscriptions, new multi-workspace product, external guests/client access, public sharing/intake, AI agents, enterprise SAML/SCIM, integrations other than GitHub, native clients and collaborative multi-cursor editing.

## Source baseline

Official Linear documentation reviewed through web research during this audit:

- S1: [Triage](https://linear.app/docs/triage) — team intake/review queue, distinct from personal Inbox.
- S2: [Issue templates](https://linear.app/docs/issue-templates) — preset properties/descriptions and structured intake; workspace/team scopes.
- S3: [Custom views](https://linear.app/docs/custom-views) — persistent filtered lists/boards that can be saved/shared.
- S4: [Project milestones](https://linear.app/docs/project-milestones) — issue grouping into project stages with progress.
- S5: [Project updates](https://linear.app/docs/project-updates) — authored health/status updates and stakeholder feed.
- S6: [Initiatives](https://linear.app/docs/initiatives) — strategic objectives grouping projects and rolling up progress.
- S7: [Cycles](https://linear.app/docs/cycles) — scheduled team delivery periods, unfinished-work rollover and estimates/capacity.
- S8: [Private teams](https://linear.app/docs/private-teams), [Roles and permissions](https://linear.app/docs/roles-and-permissions) — membership/access boundaries. Exact REKA private-team administrator behavior requires the policy decision below.
- S9: [Recurring issues](https://linear.app/docs/recurring-issues), [Issue relations](https://linear.app/docs/issue-relations) — scheduled issue creation, blocking/related/duplicate relations.
- S10: [Insights](https://linear.app/docs/insights) — filtered historical delivery analytics. REKA implements the scoped basic metrics, not every commercial report.

Research established baseline semantics, not an exhaustive authenticated inspection of Linear. Granular shared-view editor permissions, recurrence edge cases, advanced hierarchy and capacity forecasting are not assumed identical to Linear. They must use explicit REKA acceptance rules. Unsupported/uncertain details are not evidence of implementation completeness.

## Existing implementation evidence

Read-only code audit:

- `apps/api/src/auth/{auth.service,auth.guard,auth.controller}.ts`: session authentication exists, GitHub callback creates users, but workspace membership is not checked; OAuth state/verified-email enforcement needs review.
- `packages/database/src/schema/{users,organizations,teams,projects,issues,activities,cycles,comments}.ts`: organization/team/project membership and issue relations/attachment tables exist; private team, invitation lifecycle, documents and historical delivery model do not. Migration 0000 already created `milestones` and `issues.milestone_id`, but current source/schema snapshot 0003 no longer models them. Preserve those physical objects and any existing rows; do not blindly regenerate/drop/recreate them.
- `apps/api/src/{issues,projects,teams,users,cycles,comments,search,activities}/*.service.ts`: supported CRUD flows are present, but most queries do not enforce workspace/team access. Global user-role edit/delete endpoints require protection. New private-team access cannot be UI-only.
- `apps/api/src/issues/issues.service.ts`: properties and sub-issue reads exist; relations lack endpoints; identifier allocation is read-then-insert; parent hierarchy, nullable assignment, zero estimates and changed-team consistency need validation. Status activity is non-transactional and not emitted uniformly by workers.
- `apps/api/src/cycles/cycles.service.ts`: explicit close/backlog/next-cycle rollover exists, but closure is not transactional, next-cycle/team validation and scheduling/history require work.
- `apps/api/src/notifications/notifications.service.ts`: personal read/update/delete scope already uses authenticated user. Generated recipients still need private-team/subscription/preference checks.
- `apps/api/src/comments/comments.service.ts`: comments/mention notification flows exist; no comment edit/delete, subscriptions or upload service. Mention matching and recipient access require validation.
- `apps/api/src/search/search.service.ts`: title/identifier/name substring search exists for issues/projects, without private-team scope; command palette is primarily navigation, including a create command that only navigates.
- `apps/api/src/github/webhooks/webhooks.service.ts`: persisted event and queue path exist; signature validation is conditional and reserializes JSON. Fail-closed signature/raw-body validation and queue recovery need work.
- `apps/worker/src/processors/github-pr-event.ts`: status/recipient processing exists; replay deduplication is read-before-write and concurrent retries/historical activity require checks.
- `apps/web/src/features/issues/`: grouped/flat/board, selection, inline properties, sub-issues and context menus exist. Saved view/filter persistence is incomplete; estimates/dates/relations/workflow editing need end-to-end work. My Issues fallback can show work not assigned to the viewer and must match its stated scope.
- `apps/web/src/features/projects/`: project properties, descriptions, issues, members and repository linking exist. Do not count a rich description as standalone document management.
- `apps/web/src/features/dashboard/`: current attention/deadlines/cycles/review data exists; aggregate counts are not historical metrics.

## Security / data migration decisions

Must resolve before releasing membership enforcement or applying migrations to existing data:

1. **Confirmed by user:** no automatic private-content access; explicit private-team membership required even for owner/admin. Workspace administration does not grant private-content visibility.
2. **Confirmed by user:** preserve existing users as workspace members and preserve their roles; new identities require an invitation. Initial owner designation is explicit, never first-login. Implementation migration must reject ambiguous multiple existing organizations rather than granting every user access to every organization. Ask for the owner identity before any existing-data bootstrap if none is assigned; isolated test fixtures have explicit owners.
3. **Confirmed by user:** copyable expiring, single-use invitation link bound to a verified GitHub email. Email-provider delivery is not required. Do not send live invitations automatically.
4. Attachment infrastructure and live GitHub validation: provider/credentials are dependencies, not evidence of completed workflows. Resolve during the related milestone; no paid provisioning or live account actions without consent.
5. **Confirmed by user:** existing guest/client identities retain their labels and accounts as internal read-only users. No external portal or automatic promotion; private reads require explicit team membership. Personal Inbox state remains usable.
6. **Confirmed by user:** private membership is managed only by authorized existing members (lead or owner/admin already in the team). Non-member workspace admins cannot manage private membership or enroll themselves.
7. **Confirmed by user:** owner/admin/member can create teams and self-join public teams; the creator becomes lead. Read-only legacy roles cannot create teams.

Implementation decisions that do not expand scope can be recorded here. Any newly discovered product-level ambiguity or requested scope change must be confirmed, not silently added or excluded.
